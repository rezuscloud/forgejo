# 03 — Generator `--parity-out` (automation)

**Status:** done — generator extended, parity map generated and consumed by the test
**Depends on:** 02
**Blocks:** —

## Goal

Move the hand-maintained parity map (issue #02) into the swagger generator so
the drift check is itself **generated** from the spec, not maintained by hand.
This is the monorepo automation payoff: a change to the main product (the
swagger spec) automatically reflects on the auxiliary tool (the CLI parity
contract) and fails the build if the mapping breaks.

## Proposal

Extend `client-go/gen/main.go` with a fourth output flag `--parity-out`,
emitting `fj/pkg/cmd/zz_generated_parity.go`:

```go
// Code generated by api/gen; DO NOT EDIT.
package cmd

// CommandToOperation maps each hand-written UX command to the swagger
// operationId it must call. The operationId set is validated against the
// spec at generation time; the CLI parity test re-validates at test time.
var CommandToOperation = map[string]string{
    "issue create": "issueCreateIssue",
    "issue view":   "issueGetIssue",
    // ...
}
```

The generator reads a small **annotation table** authored once (a YAML/Go map
alongside the generator: `gen/parity.yaml`, mapping `fj` command path →
swagger `operationId`). On each run it:

1. Resolves every value against `swagger.json` `operationId`s.
2. Emits the Go map.
3. Fails generation (non-zero exit) if any mapped `operationId` is absent —
   so the post-merge hook's regen step fails the sync PR before it is pushed.

## Acceptance criteria

- [x] `TestCodegenClean` asserts committed `zz_generated_*` outputs match a

## Monorepo principle

Google's monorepo testing maxim: *the build graph is the source of truth; a
change anywhere triggers tests everywhere.* Here the graph edge is
`swagger.json → generator → SDK + CLI + parity map → tests`, all in one
commit, validated by one gate. The Rust split (`forgejo-api` crate →
`forgejo-cli` binary) cannot express this edge; the monorepo can.
